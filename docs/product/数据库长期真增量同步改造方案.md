# 数据库长期真增量同步改造方案

## 1. 背景

当前本地数据库文件为：

```text
/Users/bournelll/Desktop/线索运营/leads.db
```

数据库当前约 3.1G。随着本地数据持续增长，如果每次同步云端都上传完整数据库，并在云端重建 DuckDB，耗时会越来越长，且同步成本会随数据总量线性增长。

当前需要补充一个关键前提：

```text
leads.db 的基础业务数据目前由另一套服务手动同步维护。
本线索运营监控系统主要读取 leads.db，并将其同步到云端后重建或刷新分析库。
```

因此，本文里的“本地增量落库、行级变更日志、导入批次”等能力，优先应落在“维护 leads.db 的那套服务”中，而不是默认由本监控系统直接改造基础数据导入链路。本监控系统更适合作为：

1. `leads.db` 的只读消费方。
2. 云端同步发布方。
3. DuckDB / Parquet 分析数据集市构建方。
4. 在上游暂不支持变更日志时，提供快照 diff 兜底的增量导出方。

长期目标应从“同步整个数据库文件”转为“同步数据变化”。

推荐长期方向：

```text
源头变更捕获 -> 基础数据维护服务增量落库 -> 记录行级变更日志 -> 上传增量包 -> 云端合并 -> 定期全量校验
```

## 3. 结论

从长期看，第一档方案仍然是最优方向：

```text
源数据提供稳定主键、更新时间、删除标记、批次号或 CDC 日志。
```

但落地时不能只依赖 `updated_at`。更完整、可长期演进的方案应包括：

1. 每张业务表有稳定唯一主键。
2. 每次导入有批次记录。
3. 每行新增、修改、删除都进入本地变更日志。
4. 云端只消费变更日志，不再每次接收完整数据库。
5. 定期做全量校验，防止增量链路漂移。

因此，推荐建立一套“本地变更日志 outbox”机制。

结合当前实际分工，推荐结论应调整为：

| 方案 | 变更日志生成位置 | 适用性 | 评价 |
| --- | --- | --- | --- |
| A. 基础数据维护服务生成 outbox | 另一套维护 `leads.db` 的服务 | 最推荐 | 最接近真实变更，能准确区分新增、修改、删除 |
| B. 监控系统基于快照 diff 生成 outbox | 本线索运营监控系统 | 可作为过渡 | 不改上游，但需要定期扫描大表，删除语义仍需谨慎 |
| C. 继续上传完整 `leads.db` | 当前方式 | 短期可用 | 简单稳定，但耗时随数据库体积持续增长 |

如果另一套服务可以改造，应优先采用 A；如果短期无法改造上游，可以先采用 B，在监控系统内对新旧快照做 hash 对比并导出增量包。

## 4. 目标架构

### 4.1 当前模式

```text
本地 SQLite leads.db
  -> 上传完整数据库
  -> 云端重建 DuckDB
```

问题：

- 数据库越大，同步越慢。
- 每次同步成本和全量数据规模绑定。
- 云端重建 DuckDB 会重复处理大量未变化数据。
- 无法清晰追踪每次到底变化了哪些行。

### 4.2 推荐模式

```text
源系统 / Excel / 人工维护数据
  -> 基础数据维护服务
  -> 本地 SQLite leads.db 业务表
  -> sync_batches 记录维护批次
  -> sync_changes 记录行级变化
  -> 导出增量包 JSONL / Parquet
  -> 云端 DuckDB / Parquet 执行 upsert/delete
  -> sync_state 记录云端同步进度
```

核心变化：

```text
同步单位从“数据库文件”变成“行级变更记录”。
```

### 4.3 过渡模式：监控系统快照 diff

如果短期内无法改造基础数据维护服务，可以先让监控系统在每次拿到新版 `leads.db` 后做快照 diff：

```text
新版 leads.db
  -> 读取业务表主键和 row_hash
  -> 对比上一轮 sync_row_state
  -> 生成 sync_changes
  -> 导出增量包
  -> 云端合并
```

该模式需要在监控系统自己的管理库或独立 SQLite 文件中保存 `sync_row_state`，不要回写源 `leads.db`，以免和基础数据维护服务职责混杂。

示例结构：

```sql
CREATE TABLE IF NOT EXISTS sync_row_state (
    table_name TEXT NOT NULL,
    primary_key TEXT NOT NULL,
    row_hash TEXT NOT NULL,
    seen_at TEXT NOT NULL,
    PRIMARY KEY (table_name, primary_key)
);
```

限制：

- 每次仍需要扫描参与同步的业务表，但上传和云端合并只处理变化行。
- 只有确认本轮数据是全量快照时，才能把 `sync_row_state` 中存在但新版表缺失的主键判定为 delete。
- 如果新版 `leads.db` 只是窗口增量或局部刷新，不能根据缺失主键生成 delete。

## 5. 第一步最小可行方案：业务表同步元字段

在当前“两套服务独立”的前提下，第一步建议先改造维护 `leads.db` 的基础数据服务：在 6 张基础业务表中增加统一的同步元字段。

涉及表：

| 表名 | 建议主键或唯一键 | 备注 |
| --- | --- | --- |
| `线索表` | `id` | 当前无重复，建议加唯一索引 |
| `跟进表` | `id` | 已是主键 |
| `人员表` | `员工编号` | 已是主键 |
| `门店表` | `店编号` | 当前无重复，建议加唯一索引 |
| `线上实销表` | `成交编号` | 当前无重复，建议加唯一索引 |
| `外呼表` | `call_id` 或源系统通话唯一 ID | 必须先补稳定唯一键，否则只能做追加增量 |

建议每张表新增字段：

```sql
sync_created_at TEXT,
sync_updated_at TEXT,
sync_batch_id INTEGER,
row_hash TEXT,
is_deleted INTEGER NOT NULL DEFAULT 0,
deleted_sync_at TEXT
```

字段含义：

| 字段 | 说明 |
| --- | --- |
| `sync_created_at` | 该行第一次进入 `leads.db` 的时间 |
| `sync_updated_at` | 该行最近一次被基础数据维护服务真实写入或变更的时间 |
| `sync_batch_id` | 基础数据维护服务的同步批次位点，建议全局递增 |
| `row_hash` | 当前行业务字段 hash，用于判断是否真的变化 |
| `is_deleted` | 软删除标记，0 表示有效，1 表示已删除 |
| `deleted_sync_at` | 删除事件进入本地库的时间 |

其中最关键的是：

```text
sync_batch_id + sync_updated_at + row_hash
```

`sync_batch_id` 用作增量同步位点，比单纯依赖时间更稳定；`sync_updated_at` 方便排查和人工核对；`row_hash` 用于避免把未变化的重复写入误判为增量。

### 5.1 基线初始化

首次上线时，对 6 张基础表做一次 baseline：

```text
所有历史有效行：
sync_created_at = 当前基线时间
sync_updated_at = 当前基线时间
sync_batch_id = 当前基线批次 ID
row_hash = 按业务字段计算
is_deleted = 0
deleted_sync_at = NULL
```

示例：

```text
baseline_time = 2026-05-26 23:00:00
baseline_batch_id = 202605260001
```

这一步的作用不是识别历史变化，而是给云端和本地建立统一起点。完成 baseline 后，云端可以选择执行一次全量同步，之后再进入增量同步。

### 5.2 后续维护服务写入规则

从 baseline 之后，维护 `leads.db` 的基础数据服务必须按以下规则写入：

| 场景 | 写入规则 |
| --- | --- |
| 新增行 | 写入业务字段、`sync_created_at`、`sync_updated_at`、`sync_batch_id`、`row_hash` |
| 已有行且 `row_hash` 变化 | 更新业务字段、`sync_updated_at`、`sync_batch_id`、`row_hash` |
| 已有行但 `row_hash` 不变 | 不更新业务字段，不刷新 `sync_updated_at`，不刷新 `sync_batch_id` |
| 源系统明确删除 | 设置 `is_deleted = 1`、`deleted_sync_at`、`sync_updated_at`、`sync_batch_id` |

关键原则：

```text
只有真实新增、真实修改、真实删除，才推进该行的 sync_batch_id。
```

不能每次同步都把窗口内所有数据的 `sync_updated_at` 和 `sync_batch_id` 全量刷新。否则虽然可以按批次查出“增量”，但其中会包含大量未变化的伪增量，云端仍会重复处理很多数据。

### 5.3 第一阶段增量导出方式

云端同步进度记录最近一次成功处理的批次：

```text
last_synced_batch_id = 202605260001
```

下一次只导出：

```sql
SELECT *
FROM "线索表"
WHERE sync_batch_id > :last_synced_batch_id
ORDER BY sync_batch_id, id;
```

其他表同理，按各自主键排序。

第一阶段可以先不要求生成 `sync_changes`，而是按表导出“当前最新行状态”。云端处理原则：

| 本地行状态 | 云端动作 |
| --- | --- |
| `is_deleted = 0` | 按主键 upsert |
| `is_deleted = 1` | 按主键 delete 或软删除 |

成功后，云端记录本次处理到的最大 `sync_batch_id`。

### 5.4 与 `sync_changes` 的衔接

这套同步元字段可以自然升级到后续 `sync_changes` 真增量方案。

原因是后续写 `sync_changes` 所需的基础信息已经具备：

| `sync_changes` 需要的信息 | 来自哪里 |
| --- | --- |
| 业务主键 | 各表主键或唯一键 |
| 批次 | `sync_batch_id` |
| 变更时间 | `sync_updated_at` / `deleted_sync_at` |
| 是否真的变化 | `row_hash` |
| 删除语义 | `is_deleted` / `deleted_sync_at` |
| 变化后的行内容 | 当前业务表行 |

升级时只需要在维护服务的新增、修改、删除分支里，额外写入一条 `sync_changes`：

```text
新增行 -> sync_changes.operation = insert
row_hash 变化 -> sync_changes.operation = update
明确删除 -> sync_changes.operation = delete
```

也就是说，第一阶段先做到“按批次拉取变化后的最新行状态”；第二阶段再升级为“按行级变更日志重放每一次变化”。

## 6. 建议新增系统表

如果采用“基础数据维护服务生成 outbox”，以下系统表建议放在维护服务写入的数据库或维护服务自己的同步库中。

如果采用“监控系统快照 diff 过渡模式”，以下系统表建议放在监控系统独立管理库中，不建议直接写入由另一套服务维护的源 `leads.db`。

### 6.1 导入批次表：`sync_batches`

用于记录每次导入或同步任务。

建议结构：

```sql
CREATE TABLE IF NOT EXISTS sync_batches (
    batch_id INTEGER PRIMARY KEY AUTOINCREMENT,
    source_name TEXT NOT NULL,
    source_file_name TEXT,
    import_type TEXT NOT NULL,
    import_scope TEXT NOT NULL,
    started_at TEXT NOT NULL,
    finished_at TEXT,
    status TEXT NOT NULL,
    row_count INTEGER DEFAULT 0,
    inserted_count INTEGER DEFAULT 0,
    updated_count INTEGER DEFAULT 0,
    deleted_count INTEGER DEFAULT 0,
    error_message TEXT
);
```

字段说明：

| 字段 | 说明 |
| --- | --- |
| `batch_id` | 维护或 diff 批次 ID |
| `source_name` | 来源名称，例如基础数据维护服务、线索导入、跟进导入、外呼导入 |
| `source_file_name` | 原始文件名 |
| `import_type` | 导入或识别方式，例如 Excel、API、CDC、snapshot_diff |
| `import_scope` | 数据范围，例如 full_snapshot、incremental_window、id_refresh、append_only |
| `status` | running、success、failed |

### 6.2 行级变更表：`sync_changes`

用于记录每一行数据的新增、修改、删除。

建议结构：

```sql
CREATE TABLE IF NOT EXISTS sync_changes (
    change_id INTEGER PRIMARY KEY AUTOINCREMENT,
    batch_id INTEGER NOT NULL,
    table_name TEXT NOT NULL,
    primary_key TEXT NOT NULL,
    operation TEXT NOT NULL,
    row_hash TEXT,
    changed_at TEXT NOT NULL,
    payload_json TEXT,
    FOREIGN KEY (batch_id) REFERENCES sync_batches(batch_id)
);
```

建议索引：

```sql
CREATE INDEX IF NOT EXISTS idx_sync_changes_change_id
ON sync_changes(change_id);

CREATE INDEX IF NOT EXISTS idx_sync_changes_table_pk
ON sync_changes(table_name, primary_key);

CREATE INDEX IF NOT EXISTS idx_sync_changes_batch_id
ON sync_changes(batch_id);
```

字段说明：

| 字段 | 说明 |
| --- | --- |
| `change_id` | 全局递增变更位点 |
| `batch_id` | 所属导入批次 |
| `table_name` | 业务表名 |
| `primary_key` | 业务主键值 |
| `operation` | insert、update、delete |
| `row_hash` | 当前行内容 hash |
| `changed_at` | 本地记录变化的时间 |
| `payload_json` | 变化后的整行数据；delete 可为空或只存主键 |

### 6.3 同步进度表：`sync_state`

用于记录不同云端目标已经同步到哪个位置。

建议结构：

```sql
CREATE TABLE IF NOT EXISTS sync_state (
    target_name TEXT PRIMARY KEY,
    last_synced_change_id INTEGER NOT NULL DEFAULT 0,
    last_synced_at TEXT,
    status TEXT NOT NULL DEFAULT 'active'
);
```

示例：

```text
target_name = cloud_duckdb
last_synced_change_id = 123456
```

下一次同步只需要导出：

```sql
SELECT *
FROM sync_changes
WHERE change_id > 123456
ORDER BY change_id;
```

## 7. 业务表改造建议

### 7.1 `线索表`

当前情况：

- `id` 无重复。
- 已有普通索引 `idx_id`。
- 但 `id` 不是主键，也不是唯一约束。

建议：

```sql
CREATE UNIQUE INDEX IF NOT EXISTS ux_leads_id
ON "线索表"(id);
```

长期如可重建表结构，建议把 `id` 定义为主键。

导入逻辑改造：

1. 按 `id` 判断新增或已有。
2. 计算业务字段 `row_hash`。
3. 如果 hash 不变，不更新、不写变更日志。
4. 如果 hash 变化，更新业务表，并写 `sync_changes`。
5. 新增行写 `insert` 变更。

注意：

- 当前“最近31天导入”不能用来判断删除。
- 只有全量快照或源系统明确给删除标记时，才能写 `delete`。

### 7.2 `跟进表`

当前情况：

- `id` 是主键。
- 行数最大，约 684 万。

建议：

- 保留 `id` 作为主键。
- 优先改造为行级增量日志，因为该表收益最大。

导入逻辑改造：

1. 按 `id` 判断新增或已有。
2. 对整行业务字段计算 `row_hash`。
3. 只对变化行执行 update。
4. 每个 insert/update 写入 `sync_changes`。

### 7.3 `外呼表`

当前情况：

- 没有主键。
- 当前导入方式是追加导入。
- 文件内有空关键字段和重复跳过逻辑，但不能保证跨批次准确去重。

这是当前增量同步中最大的结构性短板。

优先建议：

如果源数据有通话记录唯一 ID，直接使用源 ID 作为主键。

如果源数据没有唯一 ID，建议生成 `call_id`：

```text
call_id = hash(客户电话 + 座席工号 + 开始时间 + 呼叫类型 + 通话时长 + 录音)
```

建议改造：

```sql
ALTER TABLE "外呼表" ADD COLUMN call_id TEXT;

CREATE UNIQUE INDEX IF NOT EXISTS ux_call_id
ON "外呼表"(call_id);
```

注意：

- SQLite 添加列后不能直接把已有列设为 NOT NULL，需要分阶段迁移。
- 历史数据需要先回填 `call_id`，确认无重复后再加唯一索引。
- 如果生成规则不稳定，外呼表仍然无法做到严格真增量。

### 7.4 `人员表`

当前情况：

- `员工编号` 是主键。
- 数据规模较小。

建议：

- 保持现有主键。
- 导入时增加 row_hash 判断。
- 新增/修改写入 `sync_changes`。
- 如果人员离职不删除，而是更新 `员工状态` 或 `在职状态`，应作为 update 同步。

### 7.5 `门店表`

当前情况：

- `店编号` 无重复。
- 但表结构未声明主键。

建议：

```sql
CREATE UNIQUE INDEX IF NOT EXISTS ux_store_code
ON "门店表"("店编号");
```

导入逻辑：

- 按 `店编号` upsert。
- 变化时写入 `sync_changes`。

### 7.6 `线上实销表`

当前情况：

- `成交编号` 由代码生成。
- 当前无重复，但表结构未声明唯一约束。

建议：

```sql
CREATE UNIQUE INDEX IF NOT EXISTS ux_sales_deal_id
ON "线上实销表"("成交编号");
```

导入逻辑：

- 按 `成交编号` upsert。
- `是否参与计算` 属于派生字段，也应进入 payload，保证云端结果一致。

## 8. 删除语义

删除是增量同步里最容易出错的部分。

不能简单认为：

```text
这次文件里没有出现的主键 = 应该删除
```

因为当前导入文件可能只是最近31天、某个范围、某批 ID，而不是全量快照。

建议定义导入范围：

| import_scope | 含义 | 是否可判断删除 |
| --- | --- | --- |
| `full_snapshot` | 全量快照 | 可以 |
| `incremental_window` | 时间窗口增量，例如最近31天 | 不可以 |
| `id_refresh` | 指定 ID 刷新 | 不可以 |
| `append_only` | 只追加 | 不可以 |
| `cdc` | 源系统变更日志 | 可以，前提是有 delete 事件 |

只有以下情况可以写 `delete` 到 `sync_changes`：

1. 源系统明确提供删除标记。
2. 源系统提供 CDC delete 事件。
3. 当前导入文件明确是全量快照，并且业务确认缺失主键代表删除。

否则，删除应当暂不处理，避免误删云端数据。

## 9. `row_hash` 设计

建议每张表对业务字段计算 `row_hash`。

用途：

- 判断导入行是否真的发生变化。
- 避免重复更新。
- 减少 `sync_changes` 体积。
- 支持云端校验。

计算规则建议：

1. 排除同步系统字段，例如 `row_hash`、`batch_id`、`changed_at`。
2. 字段按固定顺序排序。
3. 空值统一转换为空字符串。
4. 使用稳定 JSON 序列化。
5. 计算 SHA-256。

伪代码：

```text
normalized_row = {
  "字段A": "值A",
  "字段B": "值B"
}

row_hash = sha256(json.dumps(normalized_row, ensure_ascii=False, sort_keys=True))
```

## 10. 云端同步方式

### 10.1 增量包格式

建议优先使用 JSONL 或 Parquet。

初期建议 JSONL，简单直观：

```jsonl
{"change_id":1,"table_name":"线索表","primary_key":"abc","operation":"insert","payload_json":{...}}
{"change_id":2,"table_name":"跟进表","primary_key":"def","operation":"update","payload_json":{...}}
```

数据量上来后，可改成 Parquet：

```text
sync_exports/
  batch_000001.parquet
  batch_000002.parquet
```

### 10.2 云端合并逻辑

云端处理原则：

| operation | 云端动作 |
| --- | --- |
| insert | upsert |
| update | upsert |
| delete | delete |

处理完成后更新云端同步位点：

```text
last_synced_change_id = 本次成功处理的最大 change_id
```

如果失败，不更新位点，下次从旧位点重放。

### 10.3 DuckDB 与 Parquet 的关系

不建议长期把 DuckDB 文件作为唯一同步对象。

更推荐：

```text
云端数据底座：Parquet 分区文件
查询引擎：DuckDB
```

DuckDB 可以直接查询 Parquet，也可以定期生成一个查询加速用 `.duckdb` 文件。

## 11. 推荐实施顺序

### 阶段一：打基础

目标：不改变现有业务使用方式，但开始记录变化。

任务：

1. 明确变更日志落点：
   - 优先改造维护 `leads.db` 的另一套服务。
   - 如果上游暂不可改，则在监控系统独立管理库中做快照 diff。
2. 在 6 张基础表中新增同步元字段：
   - `sync_created_at`
   - `sync_updated_at`
   - `sync_batch_id`
   - `row_hash`
   - `is_deleted`
   - `deleted_sync_at`
3. 做一次 baseline 初始化，给所有历史有效行写入统一基线批次和 `row_hash`。
4. 改造维护服务写入逻辑：
   - 新增行写入同步元字段。
   - 已有行仅在 `row_hash` 变化时刷新同步元字段。
   - 删除只在源系统明确删除时写入软删除字段。
5. 给已有稳定键加唯一约束：
   - `线索表.id`
   - `门店表.店编号`
   - `线上实销表.成交编号`
6. 解决或暂缓 `外呼表` 唯一键：
   - 有源系统通话唯一 ID 时直接使用。
   - 没有时生成并验证 `call_id`。
7. 增加统一工具函数：
   - 计算 `row_hash`
   - 写入 batch
   - 按 `sync_batch_id` 导出变化行
8. 建立云端同步位点：
   - 第一阶段记录 `last_synced_batch_id`。
   - 升级 `sync_changes` 后再记录 `last_synced_change_id`。

### 阶段二：改造大表导入

目标：优先减少最大数据表的同步成本。

任务：

1. 如果由基础数据维护服务负责 outbox，则改造维护服务中的 `线索表` 写入逻辑。
2. 如果由监控系统做过渡 diff，则先实现 `线索表`、`跟进表` 的主键 + row_hash 快照对比。
3. 对 unchanged 行跳过更新和日志写入。
4. 输出每次导入的变更数量。

### 阶段三：解决外呼表主键

目标：让 `外呼表` 可以进入真增量。

任务：

1. 确认源数据是否有通话记录唯一 ID。
2. 如没有，定义 `call_id` hash 规则。
3. 回填历史 `call_id`。
4. 检查重复。
5. 创建唯一索引。
6. 将追加导入改成 upsert。

### 阶段四：云端消费增量

目标：不再上传完整数据库。

任务：

1. 导出 `sync_changes` 中未同步记录。
2. 上传增量包。
3. 云端按表执行 upsert/delete。
4. 云端保存 `last_synced_change_id`。
5. 成功后本地或云端更新同步状态。

### 阶段五：校验和治理

目标：确保长期准确。

任务：

1. 每日或每周做表级行数校验。
2. 每周或每月做分区 checksum 校验。
3. 保留最近一段时间的变更日志。
4. 对历史变更日志做归档。
5. 设定失败重试与告警机制。

## 12. 待确认问题

以下问题会影响最终落地方案，需要进一步确认：

0. 维护 `leads.db` 的另一套服务是否可以改造？
   - 如果可以，outbox 应优先放在那套服务。
   - 如果不可以，监控系统先采用快照 diff 过渡方案。

1. 当前“同步到云端并重建 DuckDB”的云端环境是什么？
   - GitHub？
   - 云服务器？
   - 对象存储？
   - 某个 Web 服务？

2. 云端最终必须保留 `.duckdb` 文件吗？
   - 如果必须保留，需要设计云端定期合成 DuckDB。
   - 如果可以接受 Parquet + DuckDB 查询，长期成本更低。

3. `线索表` 的源 Excel 或源系统是否有以下字段？
   - 源系统更新时间
   - 删除标记
   - 导出批次号
   - 数据版本号

4. `跟进表` 的源数据是否有更新时间？
   - 当前有 `创建时间`，但这不等于更新时间。
   - 如果跟进记录创建后可能被修改，就需要更新时间或本地 hash 比对。

5. `外呼表` 的源数据是否有通话记录唯一 ID？
   - 如果有，应直接作为主键。
   - 如果没有，需要确认用哪些字段生成 `call_id` 最稳定。

6. 当前导入文件是否存在“全量快照”类型？
   - 如果有，可以用于删除识别。
   - 如果没有，不应根据缺失主键自动删除。

7. 是否允许对当前 SQLite 表做结构迁移？
   - 只加系统表和唯一索引，风险较低。
   - 重建表并改主键，风险更高，但结构更干净。

8. 云端同步失败时，希望采用哪种恢复策略？
   - 从 `last_synced_change_id` 重放。
   - 重新导出某个批次。
   - 定期全量校验后修复。

## 13. 建议的长期最优形态

最终推荐形态：

```text
本地 SQLite:
  - 保留业务表
  - 保留 sync_batches
  - 保留 sync_changes
  - 保留 sync_state

同步过程:
  - 只导出 change_id 大于上次同步位点的变更
  - 云端按变更合并
  - 成功后推进同步位点

云端数据:
  - 优先使用 Parquet 分区作为长期数据底座
  - DuckDB 作为查询引擎
  - 必要时生成查询加速用 DuckDB 文件
```

这套方案的核心价值是：

1. 同步耗时与“变化量”相关，而不是与“数据库总量”相关。
2. 每次变化可追踪、可重放。
3. 云端失败后可以从同步位点恢复。
4. 未来源系统如果提供 CDC、更新时间、删除标记，可以平滑接入。
5. 不必长期依赖完整数据库文件上传和云端重建。
